    \section{Introduction}

    This project implements and evaluates the approach from Paper 2, which aims to make counting
    sort faster by improving data locality. The main point is that asymptotic complexity does not
    tell the whole story: in practice, counting sort can be much slower on random input than on
    sorted input even though both cases still have the same $O(n + r)$ bound.

    The paper explains this gap in terms of memory access. Counting sort repeatedly updates
    \texttt{count[value]}; when the values are scattered, those updates jump around memory and
    trigger more cache misses. When nearby elements tend to hit nearby counters, the same work
    stays within a smaller region of memory and becomes cheaper.

    We test that idea on our own hardware using a Java implementation of the hybrid pipeline, then
    compare our results with the paper's three benchmark families.


    \section{Cache-Aware Hybrid Counting Sort (Proposed Method)}

    Instead of running one global counting-sort pass, Paper 2 uses a two-stage method:

    \begin{enumerate}
        \item \textbf{Preprocess with modified quicksort.} Partition using median-of-three pivots.
        \item \textbf{Early stop using threshold rule.} Stop recursion when
        \[
            (\max - \min) + \text{size} \leq C.
        \]
        \item \textbf{Partition-local counting sort.} Run counting sort separately in each accepted partition.
    \end{enumerate}

    The idea is to spend some time reorganizing the data up front, then earn that time back
    through smaller and more cache-friendly counting passes.

    \subsection{What This Changes Relative to Baselines}

    Compared with classic counting sort, the hybrid replaces one large range-dependent count array
    with several smaller local arrays. Compared with full quicksort, it stops the partitioning
    early and switches to counting sort once partitions become value-tight. Whether this helps
    depends on the workload: it is strongest under high cache pressure and less effective when the
    preprocessing cost dominates.

    \subsection{Complexity Perspective}

    The algorithm keeps the average-case $O(n\log n)$ partitioning behavior of quicksort and
    still carries the usual quicksort-style worst-case risk under very unbalanced splits. Its
    advantage is practical rather than asymptotic: the local counting passes have better memory
    locality.

    \subsection{Design Decisions}

    \textbf{Default threshold.} We keep $C=1000$ as a paper-aligned baseline, but the reported
    runs use a tuned value of $C=16384$ for our machine. We expose both a threshold overload and a
    sweep utility because the best choice of $C$ depends on the hardware.

    \textbf{Explicit partition metadata.} \texttt{PartitionPlan} makes the preprocessing stage
    easier to inspect, test, and debug.

    \textbf{Value normalization in local counting sort.} Each partition offsets values by
    \texttt{minValue}, so the bucket array only spans the local value range. That keeps the local
    counting pass compact and improves locality.

    \textbf{Input validation.} Invalid thresholds are rejected early instead of failing deeper in
    the pipeline.

    \subsection{Correctness Checks}

    Correctness checks are now lightweight and built into the repository's command-line
    utilities. The main implementation rejects invalid thresholds at the public entry points, and
    \texttt{Improved\_CountingSortThresholdSweep.java} calls an internal
    \texttt{assertSorted(...)} check after each warm-up and measured run. In other words, the
    current \texttt{test/Improved\_CountingSortTest.java} file is a replication benchmark driver,
    not an assertion-based unit-test suite.

    \section{Experiments}

    All reported results come from benchmark methods in
    \texttt{test/Improved\_CountingSortTest.java} and were recorded in
    \texttt{your\_benchmark\_output.txt}.

    \subsection{Protocol}

    For each case, we use 3 warm-up runs and 10 measured runs, time them with
    \texttt{System.nanoTime()}, and report the average in milliseconds. Arrays are generated with
    fixed seeds to keep the runs repeatable.

    \subsection{Workloads}

    \textbf{Table 1 style (input-order sensitivity).} We compare classic counting sort on random
    and sorted data with $n=r$ over increasing input sizes.

    \textbf{Table 2 style ($r \gg n$ stress test).} Hybrid versus classic counting sort with
    $r=1{,}000{,}000$ and $n$ from 1000 to 50,000.
    We also run a Table 2.2 variant with a larger range, $r=100{,}000{,}000$, to stress cache
    capacity further.

    \textbf{Table 3 style (quicksort variants).} We compare classic quicksort,
    quicksort+insertion, and quicksort+counting for $n=r$ up to 25 million.

    \subsection{Execution Environment}

    We ran the experiments on an Intel Core i7-14650HX (16 cores) with Windows 11 and
    Temurin JDK 17.0.18. The cache hierarchy is L1 1.4 MB, L2 24 MB, and L3 30 MB. As Paper 2
    notes, cache structure and runtime details affect absolute timings, so our focus is on
    reproducing the same overall trends.

    \subsection{Why Absolute Numbers Differ}

    Our absolute timings differ from the paper because the hardware, cache hierarchy, JVM behavior
    (especially JIT and GC), and benchmark controls are all different. Those factors shift the
    crossover points, especially between Table 2.1 and Table 2.2, without changing the main trend.

    \subsection{Practical Takeaways}

    The hybrid is clearly context-dependent. It performs well under high cache pressure, but it is
    not a universal replacement for classic counting sort. The threshold $C$ should be tuned for
    the target machine and workload.

    \section{Conclusion}

    We implemented and validated Paper 2's locality-aware hybrid method and reproduced its main
    qualitative findings on our machine. Even though the asymptotic bounds stay the same, memory
    behavior has a major effect on runtime: quick+counting is strongest at large $n=r$, while in
    the $r \gg n$ setting the better method depends on how much cache pressure the count array
    creates. A natural next step would be to tune $C$ more finely around the current best value
    and report confidence intervals alongside the averages.
